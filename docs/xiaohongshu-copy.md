# 一键复制到小红书长文（2026-07-14 起）

公众号稿件页「复制到小红书」按钮：把同一篇公众号稿转成小红书长文吃得下的格式。
**不影响原有的「复制到公众号」按钮**，两条路各走各的 HTML。

## 小红书长文编辑器的真实 schema（2026-07-14 实证，不是推测）

小红书「写长文」编辑器（creator.xiaohongshu.com）是 **Tiptap / ProseMirror**。
在真实编辑器里派发 paste 事件、逐个标签测出来的白名单：

| 标签 | 结果 |
| --- | --- |
| `h1` `h2` `p` `ul/li` `ol/li` `blockquote` `mark` | ✅ 原样保留 |
| `h3` 及以下 | ⬇️ 降级成普通段落 |
| `strong` `b`（加粗）· `em`（斜体）· `a`（链接）· `code`/`pre` | ❌ 剥成纯文本 |
| `span[style]`、任何内联样式 | ❌ 一概无视 |
| `img`（外链） | ❌ 直接丢弃 |

两条推论，也是整个功能的设计前提：

1. **公众号那份 HTML 绝不能直接复用**。它满是 `<section style>` / `<span style>`，语义标签很少，
   粘到小红书会被 schema 剥成一堆纯文本——这就是「从公众号复制过来很丑」的根因。
2. **小红书没有「加粗」，唯一的行内强调手段是 `<mark>`**（工具栏的「划重点」）。

## 怎么让文案变醒目：高亮（主角）+ emoji（配角）

小红书长文里能让读者停下来的只有两样东西：**高亮**（唯一的行内强调手段）和 **emoji**（小红书的原生语感）。
两样都由 `/api/drafts/[id]/xhs-highlight` 一个接口产出。**2026-07-14 起策略定调：高亮优先、emoji 点缀**——
高亮逐段挑 1-2 句中心句撑起全文骨架；emoji 只给约 1/3-1/2 的段落（情绪/信息浓度高的），
位置模型按语感选段首或段尾（`pos: start|end`），不再清一色段首。

**模型固定走 `getFlashModel()` = `deepseek-v4-flash`**（跟 AI 标题同款轻量模型），不是写正文的 pro。

### 高亮
1. **确定性映射**：稿件 markdown 里的 `**加粗**` → `<mark>`（超过 40 字的不高亮，否则满屏黄底反而不醒目）。
2. **AI 逐段挑中心句**：整篇正文喂给 flash，每个有信息量的段落挑 1 条（信息密的最多 2 条），
   6-40 字（提示词 `xhs_highlight_system`）。实测 4237 字的稿子挑出 18 条。

**为什么 AI 那步是必需的、不是锦上添花**：不少长文风格刻意不用粗体、
不加小标题——实测一篇 4226 字的此类长文稿，粗体 0 处、`h2` 1 个。光靠确定性映射，复制过去
一处高亮都没有，就是一堵墙。加上 AI 高亮后，同一篇拿到 11 处分布均匀的高亮。

**防编造**：模型只许返回**正文里逐字出现的片段**，服务端逐条 `content.includes(p)` 校验，
对不上的直接丢弃（实测 12 条里正好丢掉 1 条被模型顺手润色过的）。所以它没有任何机会改写正文。

### 段落 emoji（提示词 `xhs_emoji_system`）
只给**值得点缀的段落**（情绪强/结论重/有反差）配 1-2 个与该段内容相关的 emoji：讲电力工厂 ⚙️、
讲思维链 🧠、引用原文 💬、自嘲 😅；平铺直叙的段落一个不配，占比控制在段落数的 1/3-1/2。
每条带 `pos`（start/end）决定插段首还是段尾——结论收尾的段尾 emoji 更像随手打的。
服务端限制**同一个 emoji 全文最多出现两次**，挡住「通篇 ✨🔥💡」的万金油偷懒。

**定位靠段落编号，不靠原文锚点**（`numberedParagraphs` / `injectEmojis`，前后端共用同一个函数）：
让模型回编号而不是回「该段开头的 8-14 个字」，输出量小一个数量级。这是性能的关键——
最初让模型逐条吐锚点，40 多个段落把响应拖到 **120 秒以上直接超时**；改成回编号后 emoji 只要 **5.8 秒**。

### 两个调用并行发
高亮和 emoji 是**两个独立的 flash 调用，`Promise.allSettled` 并行**，总耗时取两者最大值而非相加
（实测高亮 34 秒是瓶颈，emoji 5.8 秒被完全吸收，总计 34 秒）。合成一次调用会因为输出太长而超时。
一边挂了不拖累另一边，两边都挂也不阻断复制——只是退回确定性映射。

### 这条路径不走 `styledGenerateObject`（硬性约定的例外）
收口的职责是给「模型新写的正文」做风格净化（破折号→逗号等）。而这里的输出不是新正文：
高亮是从既有正文里摘出来的原文片段，必须逐字一致才能在 HTML 里定位；一旦过净化，标点被改写，
片段反而与原文对不上、全部作废。emoji 那条更是只回编号，跟正文文字无关。

## 其他转换规则（`lib/xhs.ts`）
- `h3`+ → 就近提升为 `h2`（否则被小红书降级成普通段落，白丢一层结构）
- 图片 → 原位留一行「📷 配图N：图注」，提醒手动补图（图片粘不进去，见下）
- 链接/行内代码/代码块 → 脱标签保文字（小红书反正会剥，我们主动剥干净）
- 分隔线 → 一行「· · ·」；表格 → 拍平成「单元格 ｜ 单元格」的段落
- 所有 class/style/id 属性一律清空

## 图片：带不过去，别再试了
小红书**没有**公众号那种「粘贴时自动抓取外链 `<img>` 并转存」的机制（公众号有，mdnice/doocs 全靠它）。
实测裸 `<img>`、`<figure><img>` 两种写法都被直接丢弃。图片只能走工具栏「插入图片」手动上传。

用户看到的「从公众号链接导入能带图」是另一条路：小红书长文首页的**「导入链接」**功能，
需要先在小红书关联微信公众号（关联账号 `gh_...`），由小红书**服务端**去抓取公众号文章全文，
跟浏览器粘贴完全是两套机制。想要图片一起过去，就用那条路，不是这个按钮。

## 纯文本兜底通道
剪贴板同时写 `text/plain`：把结构编码成 emoji 排版（`📌` 小标题、`1️⃣` 序号、`▪️` 要点、`💬` 引用）。
小红书手机 App 发普通笔记时用不了 HTML，这份兜底能直接用。

注意：**纯文本里塞 markdown 符号是死路**。小红书键入 `1. ` 会自动变醒目序号，靠的是 ProseMirror 的
input rules——它只响应逐字符键入，**不响应粘贴**。所以只能靠 `text/html` 通道传结构。

## 两段式交互 + 服务端中转缓存（2026-07-14 重做，别改回同步等待）

**旧版的坑**：把 pending Promise 塞进 `ClipboardItem` 让浏览器等 AI 结果——这 30-100 秒里剪贴板被挂起的
写入占住，用户中途复制的任何东西（比如正在编辑的公众号内容）都会在完成时被覆盖。已砍。

**现在的流程**：
1. **服务端中转缓存**：结果按正文指纹（`xhsContentHash`，FNV-1a×2，前后端共用）存
   `ms_sync_state` 的 `xhs_assist:<draftId>` 键。POST 先查缓存，命中毫秒级返回；
   GET `?hash=` 轻量查询就绪状态（不触发计算）。
2. **生成链路预热**：选题页/洗稿出正文后，与配图、封面**三路并行**发一次 POST 预热缓存。
   正常路径下用户到稿件页时结果早就躺在缓存里。
3. **按钮三态**：打开稿件页先 GET 查一次就绪 → 已就绪显示「复制小红书（已就绪）」，点击**同步渲染 +
   手势内写剪贴板**，秒贴；未就绪点击只是把生成踢到后台（**不碰剪贴板**），完成后提示「已就绪」，
   再点一次即秒贴。期间随便编辑、随便复制公众号。

- 实测：4237 字首次生成 108 秒（所以 `maxDuration` 给到 300），缓存命中 0.4 秒
- AI 挂了/未配置引擎都不阻断复制，退回确定性高亮（加粗→mark）
- 正文一改指纹就变，就绪态自动失效，下次点击重新生成
- 标题小红书要单独填（它的标题框是独立 input，不吃粘贴的 HTML）
